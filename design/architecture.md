# HiddenMateの構成

## 基本方針

覆面駒を`fmrs_core`の新しい駒種として実装しない。覆面駒の正体を具体化した通常局面を複数作り、それぞれの合法手・王手・詰みを`fmrs_core`で判定する。

```text
問題JSON
  │  ProblemDocument（入力検証、ルール・手数・駒台モード）
  ▼
VariableProblem
  │  候補駒種、駒の在庫、初形合法性から具体局面を列挙
  ▼
HiddenState
  ├─ ConcreteWorld (V1=飛, V2=銀)
  ├─ ConcreteWorld (V1=龍, V2=銀)
  └─ ConcreteWorld (V1=龍, V2=金)
         │
         └─ fmrs_core::PositionAux
```

覆面駒は最大6枚で、IDと配置マスは重複できない。候補駒種を省略した場合は全14駒種から始め、標準駒数の在庫、配置、二歩などの初形合法性、選択ルールに必要な玉の数によって不可能な具体世界を除外する。

## 対応ルールと手番

現在は次のルールに対応する。

- `helpmate`（協力詰）: 攻方が受方玉を詰める。
- `helpSelfmate`（協力自玉詰）: 受方が攻方玉を詰める。

探索終了時の手番は、協力詰では受方、協力自玉詰では攻方となる。初手番はこの終了手番と指定手数から逆算するため、`baseSfen`に書かれた手番は読み込み時に上書きされる。

探索は指定手数以下について、ルール上詰みになり得る手数だけを短い順に列挙する。両者が協力する存在探索であり、minimax探索ではない。指定した最大解数に達すると探索を打ち切る。

## 観測着手と候補世界の更新

具体世界では駒種が確定しているが、棋譜から未確定の覆面駒の種類は直接見えない。各世界の具体着手を`ObservedMove`へ射影し、同じ観測着手を一つにまとめる。観測着手を適用すると、その着手が合法な具体世界だけを残す。候補が一種類になった覆面駒は確定済みの通常駒として以後の手順を扱う。

持駒の覆面駒を区別しないモードでは、匿名の覆面駒打ちを一つの`ObservedMove`として扱う。内部では、その駒台から打てる各`VariableId`を選んだ具体着手へ分岐し、後続の観測と矛盾しない世界を同じ`HiddenState`へまとめて保持する。盤上へ出た後も元のIDは観測情報へ含めず、移動元マスによって駒を追跡する。

通常の着手可否、王手義務、王手回避、打歩詰めは各具体世界の`fmrs_core`局面で判定する。受方から開始する手順の初手だけは、初形で王手されていなくても着手できる。

## 詰みの証明

最終局面で、残るすべての具体世界が選択ルールの詰み条件を満たす場合だけ詰みとする。一つでも詰みでない世界があれば、詰みは証明されていない。

- 協力詰では、受方玉が王手され、合法応手がないことを確認する。
- 協力自玉詰では、攻方玉について`fmrs_core`の協力自玉詰判定を使う。

## Web・CLIからの利用

```text
React UI
  └─ VariableSolverClient
       └─ Web Worker
            └─ Wasm solve_variable_problem
                 └─ hiddenmate_core

hiddenmate_cli
  └─ hiddenmate_core
```

Web版は探索をWeb Workerで実行するため、検討中もUIスレッドを塞がず、中断時はWorkerを終了できる。問題JSONと探索結果は利用者のブラウザ内で処理し、外部サーバーへ送信しない。CLIも同じ`ProblemDocument`、候補世界列挙、探索、手順表記を使用する。

## 透明駒（駒種指定）

駒種・初期所属・枚数が判明し、位置だけが不明な透明駒を合計2枚まで扱う。透明駒の在庫は受方持駒または駒箱から割り当て、初期位置は通常駒と重ならない盤上の各マス、または所属側の駒台を候補とする。同じ所属・駒種の複数枚は個体を区別しない。

透明駒の可視駒を取らない着手は、具体的な移動元・移動先・成生を観測せず`X`へまとめる。可視駒を取った場合だけ、取られたマスを`76X`のように観測する。透明駒が取られた場合は生駒へ戻して捕獲側の透明な持駒とし、後続世界でも追跡する。所属・駒種・位置が全候補世界で共通になった駒は可視化し、以後は通常駒として扱う。

各候補世界は通常の`PositionAux`と、まだ透明な駒の匿名リストを持つ。一つの観測着手に対応する具体着手を一度にグループ化し、着手後の局面と透明駒情報を正規化して重複排除する。残るすべての世界で詰み条件が成立した場合だけ詰みとする。候補世界が20,000件を超える入力・遷移は、候補を切り捨てずエラーにする。

## 候補世界バックエンド

`HiddenState`と`KnownInvisibleState`は、具体世界を保持する明示列挙バックエンドである。覆面駒が少ない短編では検証しやすく、今後も正解基準として残す。

`ReplayHiddenState`と`ReplayKnownInvisibleState`は、初形問題・観測履歴・各手で確定した駒だけを永続保持する再生型バックエンドである。観測着手、遷移、候補照会、詰み判定が必要になった時点で初形生成器から該当世界を再生する。選択した観測分岐だけ一時的に具体化するため常駐メモリを抑えられる一方、同じ履歴を再生するCPUコストが増える。観測着手集合と詰み判定は状態単位の小さなキャッシュに保持する。

覆面駒では`VariableProblem::enumerate_replay[_with_hand_variable_mode]`、駒種指定透明駒では`KnownInvisibleProblem::enumerate_replay`で再生型状態を作る。探索にはそれぞれ`solve_replay_exact[_profiled]`、`solve_replay_known_invisible_exact[_profiled]`を使う。通常の`enumerate`と既存Web・CLIは、互換性と速度を優先して明示列挙バックエンドのままである。

透明駒では位置も未知になって組合せが増えるため、将来は同じ問題・観測境界の背後にSAT/SMTまたはBDD方式を追加することも検討する。

### 候補世界バックエンド改善の基盤

明示列挙方式を将来の共有・遅延方式に対する参照実装として残す。覆面駒は`enumerate_explicit`、駒種指定透明駒は`enumerate_explicit`で参照結果を取得でき、通常の`enumerate`と候補世界数・観測着手・解が一致することをテストする。

候補集合の内部表現には次のコンパクト表現を使用する。

- 覆面駒の14駒種候補: 16ビットの`KindSet`
- 透明駒の盤上81マスと両者の駒台: 128ビット内の83ビット
- 具体局面: 参照共有し、着手を適用する世界だけコピーするコピー・オン・ライト

`enumerate_profiled`と`solve_exact_profiled`系APIは、候補世界数、列挙時間、探索中のピーク世界数、訪問状態数、生成遷移数、後続世界数、着手生成・遷移時間を返す。通常APIの問題形式と解形式は変更しない。

再生型バックエンドは、候補世界数、観測着手、各後続状態の候補数・候補駒種・詰み判定、最終的な解について明示列挙バックエンドとの完全一致をテストする。協力詰・協力自玉詰、受先、覆面持駒の区別あり／なしを同値性テストに含める。再生型を既定化するかは、実問題でのメモリ削減量とCPU増加量を計測して別途判断する。
